## Current implementation findings

- The portfolio manifest and shared artifact list still require seven files.
- The portfolio adapter requires a specific template, approval markers on all
  documents, checkboxes, a screenshot, and a separate validation map.
- `PracticeCoordinator.toView` disables ordinary submission review for every
  portfolio profile. Its portfolio path instead uses five stage receipts.
- `PracticeReviewService` collects artifact contents for the older ContentPilot
  `planning-package` profile, but does not do so for `portfolio-planning`.
- `PortfolioModuleCompletionService.completeModuleTwo` requires version 1.0.0,
  seven artifacts, five approvals, and a first-task summary. It expects an active
  run, whereas ordinary review return archives the completed run.
- New Practice creation creates a new Executor task. The Module 2 completion
  handoff does not currently carry the task binding needed for Module 3 reuse.
- Practice review history, failure recovery, stale-result handling, and Teacher
  chat exclusion already exist and should be reused.

## Approaches considered

### Recommended: version the portfolio contract and reuse submission review

Introduce the five-document contract as portfolio Practice version 2.0.0.
Collect its files into the existing bounded review envelope, use the existing
read-only AI evaluator, and expose the existing Practice review/result controls.
Persist approval and completion against file digests and the exact bound task.
This needs targeted adapters and compatibility work but retains the established
Practice behavior and makes old receipts distinguishable from new ones.

### Alternative: keep the five-stage approval workflow

Changing only the artifact count would be smaller, but it retains mandatory
stops and approvals after each supporting document. It also leaves AI review
without the actual portfolio document contents. This does not satisfy the newer
handoff and is rejected.

### Alternative: build a separate portfolio review subsystem

A separate submission window, reviewer, and persistence store could avoid some
existing type changes, but would duplicate recovery, identity, history, and
freshness handling. It increases integration risk without a learner benefit.

## Module 2 behavior

### Required outputs

The required document set is exactly:

1. `planning/portfolio-brief.md`
2. `planning/content-evidence-inventory.md`
3. `planning/reference/reference.md`
4. `planning/PRD.md`
5. `planning/implementation-plan.md`

Validation coverage belongs in the implementation plan. Neither
`requirement-validation-map.md` nor `first-bounded-task.md` is required or
generated by the new prompt. Reference screenshots are optional supporting
evidence; when referenced, their paths, boundaries, and digests are checked.
Additional legacy documents are never deleted automatically.

Executor works in the selected portfolio workspace and the same task through
drafting, revisions, and resume. It asks only for missing information or
consequential choices, reuses settled PRD decisions, and does not add mandatory
comprehension questions. Module 2 does not create an app, install dependencies,
or publish. The learner approves the final PRD and implementation plan.

### Submission and approvals

The Practice-owned surface exposes one final-package approval/submission flow,
not five sequential stage gates. It identifies the five current documents and
lets the learner explicitly confirm approval of the PRD and plan before review.
Merely pressing a generic AI-review button must not silently become learner
approval. Text written by Executor inside a document must not become
authoritative approval either.

Approval is bound to the current workspace, course run, Practice version,
attempt, Executor task, and current document digests. The plan approval also
depends on the PRD and supporting inputs. Updating inputs makes the approval
and any successful review stale; reusing an old timestamp is not sufficient.

Submission runs deterministic checks and then the existing read-only AI
reviewer. Teacher chat remains disabled during the active Practice. The result
is a pass or a concrete list of issues referencing the affected documents.
The learner fixes issues in the same Executor task and submits again.

### Evidence and AI review

Deterministic checks establish file existence, safe canonical paths, valid UTF-8,
bounded sizes, nonempty required sections, reference integrity, requirement-ID
coverage, allowed workspace changes, approval identity, and evidence freshness.
They must not claim to prove content quality or learner understanding.

Use consistent document structure provided to Executor, but do not reject
equivalent content solely for a harmless punctuation or heading variation.
Assess substantive clarity, feasibility, alignment, missing assumptions,
privacy/publication boundaries, reference use, and useful acceptance criteria
through AI review of the actual bounded document contents.

Freeze the review inputs, compute digests locally, and re-read after AI review
and before completion. If files, approvals, task, workspace, or attempt change,
reject the outdated result. A malformed response, disconnection, busy task, or
review failure preserves the previous durable result/history and cannot pass
the Practice. Deterministic test fixtures remain explicitly simulated.

### Completion and handoff

A passed submission unlocks the existing Module 2 assessment. The existing
assessment content and navigation are retained; no extra oral or written
questions are introduced by Practice. Completing the module requires the
current passed submission, current learner approvals, current five-document
evidence, and the existing assessment gate.

Completion must work after the Practice review flow archives the active run:
retain the exact completed submission/binding needed for revalidation rather
than depending on whichever run is active later. Persist the completion receipt
before advancing progress, and keep completion idempotent after relaunch.

The versioned handoff includes the canonical workspace, five artifact
references/digests, verified submission identity, exact Executor task binding,
and a bounded summary of audience, scope, constraints, gaps, and implementation
order. It must not depend on a first-task document or treat a transcript as the
authoritative plan.

## Saved-progress migration decision

Approved behavior:

- Preserve learner files, Executor task, existing review history, and original
  completion receipts as historical records.
- Require a fresh five-document submission and review before an old Module 2
  attempt can satisfy the new completion gate.
- Do not convert old stage receipts into new approvals or AI-review success.
- Make migration idempotent and recoverable; old records must remain readable
  instead of being rejected as corrupt and reset.
- Do not silently delete the two legacy files. Their presence in a migrated
  workspace is distinguished from new out-of-scope application changes.

The alternative is to retain old rules for existing attempts and enable version
2.0.0 only for new attempts. That avoids reassessment but maintains two behavior
sets and means an old completion does not prove the new handoff requirements.
The owner selected the recommended preservation-and-fresh-review policy.

## Module 3 boundary and deferred decisions

Carry the exact Module 2 task binding forward so the implementation can continue
in that task. Validate task accessibility and workspace identity; never create
a silent replacement task if the binding is missing or inaccessible.

The handoff explicitly leaves replacement Module 3 criteria unsettled. Do not
remove the current build, debugging, independent-improvement, receipt, or
completion gates as an incidental Module 2 change. Before implementing those
changes, agree on the replacement criteria and satisfy the required Module 2
approval/acceptance gate. Theory content remains under Triết's ownership.
